capcomd is durable orchestration for swarms of coding agents. Your coding agent drives it: Claude Code and Codex agents run in parallel, each in its own VM on its own branch, and only the exact commit that passed your checks and a reviewer agent merges, once.

Spawn, await,verify, merge.

A run is a set of durable actors on Rivet. Every step is an idempotent, recorded transition: a crashed orchestrator, engine or agent driver resumes where it stopped, a retried call never acts twice, a merge happens exactly once. A chaos suite kills the process at named points, and at random, to prove it.

The orchestrator is whoever calls the primitives: your agent through the plugin, MCP or the CLI; an agent in a VM that is allowed to delegate; or you. capcomd ships primitives, not a workflow. Agents keep working when the driver's session ends.

One agent, one VM,one branch.

VMs come through one sandbox provider interface: create from a snapshot, exec, upload and download, egress allowlist, checkpoint and snapshot, suspend and resume, destroy. Orchestration, durability and the gates sit above it. boxd is the first provider and the one verified live.

Inside its VM an agent is unrestricted by default: every tool, open network. A profile narrows its tools, sandbox and egress. Writing a provider is documented in docs/providers.md.

boxd is verified live end to end; Docker sandboxes arrived in 0.6. The app learns about providers from the daemon, so a new one needs no change there.

Credentials

VM snapshots are scrubbed of secrets. An agent's VM holds its own login and a short-lived git credential for pushing its branch; a checks VM holds none. Agents never hold push credentials for your target.

Checkpoints

The engine pushes each workspace to refs/capcomd/checkpoints/<agent> every 10 minutes, after each commit and at each quarter of a budget, and deletes it once the work merges.

Continue

An agent stopped by a limit ends failed with its work on its branch. spawn --continue agt starts a new agent from that branch, or from the last checkpoint if it crashed or was cancelled.

Roles are profiles.Trees are policy.

A role is any named profile in .capcomd/agents.json: a provider (Claude Code or Codex), a login (plan or API key), a model and effort, allowed tools, a sandbox, an egress allowlist, limits, and a children block that says whether it may spawn, which profiles, how deep and how wide.

So a profile delegates only to the profiles you allow, as deep as you allow, and a parent can only narrow that for its children. capcomd agents schema prints the JSON Schema; agents validate checks a file against it.

.capcomd/agents.json{ "schema": "capcomd.agents/v1", "agents": { "worker": { "provider": "claude", "auth": "subscription" }, "codex-worker": { "provider": "codex", "auth": "subscription" }, "reviewer": { "provider": "claude", "auth": "subscription", "allowedTools": ["Read", "Glob", "Grep", "LS", "Bash(git diff:*)", "Bash(git log:*)", "Bash(git show:*)", "Bash(cat:*)", "Bash(ls:*)", "Bash(bun test:*)"] }, "planner": { "provider": "claude", "auth": "subscription", "children": { "allowSpawn": true, "allowedChildProfiles": ["worker", "codex-worker"] } } } }

What capcomd setup project writes for a repo with Claude and Codex logins and bun test as its check: one worker per provider, a read-only reviewer that may also run the check, and a planner that may spawn only the workers. No turn, time or money limits until you add them.

How they talk

Down
send: the orchestrator or a parent messages a running agent. Claude reads it at its next step, within seconds; Codex can't read messages while it runs.
Up
handoff, inbox, result: a child reports to its parent with a summary, artifacts and data; the parent also sees its branch, commit and verification.
Shared
The run's task board, with leases, epochs and ordering, and a kv blackboard written with compare-and-swap; the event stream carries both.
Fenced
Anything another agent wrote arrives as untrusted data, never instructions. Authority comes only from the agent's capability token.
Not yet
A leaf gets the board, kv and inbox only when it may spawn; siblings' messages go through their parent. Sibling messaging within one parent is on the roadmap.

What breaks at scale.What holds it.

  • Agents report success, not proof

    Checks the operator named run in a fresh VM on the branch merged with the latest target, then a separate read-only reviewer. Both must pass; no agent verifies or merges its own work.

  • Parallel agents collide

    One VM, clone and branch per agent. Each change is verified against the latest target and merges are serial and exactly once, as the commit that passed.

  • Delegation multiplies risk

    Depth, fan-out, child profiles and budget share are ceilings a parent can only narrow. Capability tokens scope every call; agent text is fenced as data. Budgets in dollars, turns and wall time are carved down the tree.

  • Long runs break

    Durable actors resume after a crash or restart; a retried call never acts twice. Workspaces checkpoint while agents work, a stopped agent continues from its branch, and a usage-limit pause resumes by itself after the reset.

  • Agents get stuck

    Idle, spinning and failing agents raise a notice to the parent and the waiting await, with the work checkpointed. A profile can add a stop after a second window; the work is kept.

  • Nobody can see what happened

    The agent tree, a span waterfall, per-agent timelines and the event log, live. Costs roll up per agent and subtree, including the API-equivalent cost of work on Claude and ChatGPT plans.

  • Machines are left behind

    Every VM is destroyed when its agent or check is done. The live run used 13 VMs, all cleaned up.

Seven patterns,one set of primitives.

The orchestration skill teaches your agent the primitives and when to use which pattern: run new, spawn, await, wait-any, send, cancel, verify, merge, the task board, kv, events, budget and grant, tree.

  1. Single loop

    spawn, await, verify; on a fail, send the failures or spawn again with them; merge.

    One coherent change.

  2. Fan-out, fan-in

    A task per disjoint area, a spawn per task, a wait-any loop that verifies each, merges in series, then one verify on the target.

    Independent subtasks.

  3. Supervisor and workers

    Workers claim leased tasks, renew, mark them done; shared decisions go through kv cas. A crashed worker's task goes to the next claim.

    A long queue of dynamic work.

  4. Critic loop

    A coder, then verify with a review profile and acceptance criteria; the reviewer's reasons go back to the coder, up to k rounds.

    A bar tests can't express. Put the critic on another provider.

  5. Best of n

    n coders on the same task, verified each; a judge agent picks among those that passed; merge the winner, cancel the rest. There is no built-in compare yet.

    High-variance, high-value changes.

  6. Hierarchical planner

    capcomd run "<goal>" spawns a planner that splits the work and verifies and merges its children from its VM; sub-planners for big areas.

    Big, multi-area goals.

  7. Interface first

    A small contract child lands first; provider and consumers then run in parallel and land in dependency order. Stacked branches aren't supported.

    Dependent work.

Plus report agents. spawn --report gives a read-only checkout; the final message is the result and nothing is pushed: research, triage, analysis.
