# Agent profiles

Named harness agents (a capcomd primitive, see ADR-016) in `.capcomd/agents.json` (override with `CAPCOMD_AGENTS_FILE`). Schema: `capcomd agents schema` (JSON Schema, id `capcomd.agents/v1`). Design: ADR-015 §5–7.

```bash
capcomd agents add rev --provider claude --auth subscription --max-turns 20 --append-system-prompt "Be terse." --default
capcomd agents add cx  --provider codex  --auth apikey --sandbox workspace-write --egress github.com
capcomd agents set rev --model claude-sonnet-4-5 ; capcomd agents set rev --unset model
capcomd agents list --json ; capcomd agents show rev --json   # spec + effective config + readiness
capcomd agents validate ; capcomd agents rm cx
capcomd run --profile rev --set maxTurns=10 --set children.maxDepth=1 "goal"   # narrowing only
capcomd run --profile rev --overrides '{"maxTurns":50}' --operator "goal"       # widening needs --operator
```

For Hermes or another orchestrator: define profiles with `agents add NAME --spec '<json>' --json`, read them with `agents list --json`, and select one per goal with `--profile`, or a per-task directive `[agent:NAME] …` in the goal text.

Limits are optional: `maxTurns`, `timeoutMs` and `maxBudgetUsd` (`--max-turns`, `--timeout-ms`, `--budget`) are unset unless you set them, and an unset limit means none (ADR-019). Turns count differently per provider: Claude Code counts model turns, Codex counts tool steps. Nothing else restricts an agent by default either: a run without `--budget` has none, a profile that may spawn has no depth or descendant limit unless its `children` block sets one, and an agent without `allowedTools` gets every tool with no permission prompts, nothing disallowed, Codex's `danger-full-access` sandbox and open egress from its VM (the VM is the boundary, and agents never hold push credentials). Narrow any of these per profile: `allowedTools`, `disallowedTools`, `sandbox`, `egress`. What is always on is a watch for an agent that looks stuck. It reads what the agent does, not how long it takes: **idle** (its CLI produced no output for `idleAfterMs`, `--idle-after-ms`, default 30 minutes), **spinning** (the same tool call with the same input `stuckRepeats` times in a row, `--stuck-repeats`, default 8) or **failing** (the same command failing with the same error `stuckRepeats` times, numbers aside). The first window is only a notice: `inspect` and `tree` show it as `notice`, the event log gets `AGENT_NOTICE`, the supervisor checkpoints the work, and `capcomd await --notices` (and `capcomd_await`, and `await` inside a VM) return early with `notices` so the parent can step in. By default that's all: the agent keeps running. A profile that sets the window (`idleAfterMs` for idle, `stuckRepeats` for spinning and failing, or `CAPCOMD_AGENT_IDLE_MS` / `CAPCOMD_AGENT_STUCK_REPEATS`) also gets a stop: if the agent is still stuck after a second window (twice the idle time, twice the repeats), it's stopped with `result.limit` idle, spinning or failing. Any stop keeps the work: it's pushed to the agent's branch and the agent ends `failed` with `result.limit`.

Budgets (`run new --budget`, `spawn --budget`) are enforced from live spend: while an agent works, its runner reports what it has spent every few seconds (Claude's from each message's token usage at list prices, until its final cost arrives; Codex's from tokens × `CAPCOMD_CODEX_USD_PER_MTOK_IN/OUT`), and the engine stops the agent (`result.limit: max_budget_usd`, work kept) when its own budget, an ancestor's or the run's is spent. A spawn reserves only the units it names (or its profile caps), so agents spawned without a budget share what's left.

Every agent runs under a small supervisor in its VM (when the VM has `node`, which the npm-installed CLIs bring). It reports a heartbeat every 30 seconds and checkpoints the workspace every `checkpointEveryMs` (`--checkpoint-every-ms`, default 10 minutes) and right after the agent commits: a commit of the working tree on top of HEAD, made through a temporary index so the agent's files, index and history are untouched. The engine pushes it to `refs/capcomd/checkpoints/<agentId>` (the VM holds no push credentials), and the agent's record shows it as `checkpoint`. To continue from one: `git fetch origin refs/capcomd/checkpoints/<agentId> && git merge FETCH_HEAD`.

When an agent's provider says its usage limit is reached (a plan's limit or the API's), the agent is `paused`, not failed: what it changed is pushed to its branch (`Capcomd-Stop: quota`) and its result has `limit: "quota"`, the login (`claude:subscription`) and `resetAt`. It runs again after the reset (when it gave none, after `CAPCOMD_QUOTA_RETRY_MS`, default an hour), as a new attempt in a new VM that continues on its branch. The login is remembered on the engine host (`quotas.json` in the state directory), so other agents on it wait for the reset instead of starting. `capcomd resume <runId> [agt]` runs paused agents now and clears the login's wait. Paused agents are woken while someone awaits them.

Auth is exactly one of `apikey` (the provider's API key, from local env or a boxd secret) or `subscription` (from `capcomd auth login claude|codex`). Giving both or neither is an error. `CAPCOMD_AGENT` still works as an override, set to a kind or a profile name.

`children` (policy only for now): `{allowSpawn, maxDepth, maxChildren, maxTotalDescendants, allowedChildProfiles, budgetShare}`. Children may only narrow their parent.
